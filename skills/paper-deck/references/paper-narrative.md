# 论文的结构 — 沿用它,别重写它

**论文和代码仓最大的不同:论文自带叙述结构。** 一个代码仓是一堆并列的模块,没有内在的"先讲什么后讲什么",所以给仓库做 deck 必须先推导一条主线出来。论文不是——作者已经花了几个月把它组织成一条论证链,每一节放在那个位置都是有理由的。

所以 paper deck 的第一原则是:**沿用论文自己的结构,把力气花在压缩和点亮上,而不是重新叙事。**

## deck 相对论文只加两样东西

你不是在替论文重新论证,你是在帮听众更快地读懂它。deck 的增量价值只有两项:

1. **总结性文字** — 把每一节压成一句"这节确立了什么",让听众不必读完整节就抓住结论。论文为了严谨会写三段,你写一句。
2. **动态交互** — 把静态图讲不动的机制拆开、一步步演出来,让人真正看懂方法怎么 work。这是纸质论文给不了的东西,也是 deck 唯一不可替代的价值。

除此之外的"增值"基本都是负价值:重新编排顺序、造一条新主线、加悬念钩子、把结论改写成更有冲击力的说法——这些都在把听众带离论文本身。

## 主线 = 论文自己的节奏

nav 词直接来自论文的章节骨架,把学术章节名换成听众能秒懂的白话即可:

| 论文里的章节 | nav 词写成 |
|-------------|-----------|
| Introduction / Motivation | `问题` 或 `动机` |
| Related Work + 引言里的 gap | `现有不足`(常可并进"问题") |
| Approach / Method / Framework | `方法` |
| Benchmark / Dataset Construction | `怎么建的` |
| Experiments / Empirical Study(RQ1…RQn) | `实验` 或直接按 RQ 分 |
| Discussion / Threats / Limitations | `局限` |
| Appendix / 形式化细节 | `技术细节` |

保持 4–6 段、词要短。只在模板脚本顶部的 `MAINLINE` 数组里定义一次,每页用 `data-sec` 认领所属段,高亮自动跟随——不要在各页手动维护 `class="active"`。

**允许的调整,仅限这几种**(都是压缩,不是重排):

- **合并**:Related Work 常可并进"问题"一段,不必单独占一段 nav。
- **省略**:与主线无关的工程细节、复现说明,整段推进技术附录。
- **按 RQ 切**:实证论文的 Experiments 常自带 RQ1–RQ4,直接用它们当段落切分比你另起炉灶更贴合。

**不允许的**:把方法挪到问题之前"制造悬念"、按"卖点强弱"重排、发明论文里不存在的段落概念。论文先讲什么后讲什么,你就先讲什么后讲什么。

**测试:** 把你的 nav 词和论文目录并排放,能一眼看出对应关系吗?对不上,就是你在重写而不是沿用。

## 每页标题 = 总结,不是钩子

每页标题写成**这一节确立了什么**的一句话——它同时满足"不是光秃秃的名词标题"和"忠实于论文"。它必须是**总结**,不是**悬念**。

这条最容易失手,所以给出真实的反面例子(取自一次真实的失败产出):

| ❌ 钩子式(在替论文加戏) | ✅ 总结式(在帮听众省时间) |
|---|---|
| 「你对这个数的直觉,大概会高出一倍。」 | 「测试通过率与设计合规几乎不相关:Cramér's V ≤ 0.1157,χ² 在多数设置下不显著。」 |
| 「agent 交出的那个 patch,正是十年前被开发者 revert 掉的方案。」 | 「Django 的这个 issue 说明:补丁通过全部测试,仍可能因违反项目既有设计约定而被拒。」 |
| 「这条流水线把 code review 里的闲聊,压成可判定的约束。」 | 「DesignHunter 两阶段从 PR 讨论中抽出 design constraint:先抽原子建议并验证采纳,再聚合成带 option 的约束。」 |

左列的毛病是**口气**:制造悬念、卖结论、用"你大概会…"这种直接对听众说话的营销腔。听众来听论文讲解,不是来听路演。右列用论文自己的术语和数字,一句话说完这节的结论——这就是"总结性文字"。

判据:这句标题,论文作者会点头说"对,这节就是这个意思"吗?如果他会觉得"我没这么说"或"你说得比我夸张",重写。

## 交互放在哪:让人看懂机制

交互不是装饰,是这份 deck 唯一比 PDF 强的地方。但正因为稀缺,它必须**投在静态图真的讲不动的地方**,而且必须**承载论文的真内容**。

**先问一句:抽原图够不够?** 够,就抽原图,别做交互。论文的图是作者反复打磨过的,你一遍手画的版本通常更差(见下一节)。只有当"看它动"能教会静态图教不了的东西时,交互才成立:

- **多阶段流水线、算法循环、状态机** → 分步演,让听众看见状态怎么流转。
- **需要对比的两种做法**(baseline vs 本文、refinement 前后)→ 切换式交互。
- **随参数变化的行为** → 可调参数。

**交互里必须是论文的真东西,不是通用方框。** 最常见的失手是画四个灰盒子写上"Stage I / Stage II / 关联 / 验证",依次点亮——听众看完只知道谁排第一,不知道每步做了什么。及格线是带上:**真实参数值**(`w = 6`、阈值 τ、三模型多数投票)、**真实数字**(`10,885 → 2,458 → 1,787 / 495` 这样的实际漏斗,不是"大量 → 较少")、**真实例子**(论文给了 case 就用那个 case 的真实代码与评论,别编示意的)。

**一个扎实的交互 + 几张忠实原图,胜过三个空壳。** 为了凑数造出来的交互是负价值:占版面,还让听众觉得这份 deck 在表演。

## 方法图 vs 结果图的分工

**默认抽原图;重画是要挣来的例外。** 论文的图是作者花几个月打磨的,里面每处细节——真实的代码 diff、评论原话、坐标轴与误差棒——都是论据本身。你一遍手画的 SVG 通常元素更少、排版更糙,而且会丢掉恰恰是这张图存在理由的那些细节。**丢细节的"提炼"是降级,不是设计。**

**重画的准入门槛(三条同时满足,少一条就抽原图):**
1. 交互真的教会了静态图教不了的东西(分步演机制 / 切换对比 / 参数变化),不是"方框依次显现";
2. 你的版本信息量不低于原图——你正准备"为了干净"删掉的字,往往就是论据;
3. 你说得出它论证的那一句话。

**动机图 / 案例图 / 定性样例图几乎总是抽原图。** 它们的全部价值就在那些具体内容,一旦被"提炼成时间线",论据就没了。**真实反面教材:** 有一版把某论文的动机图(含真实代码 diff、四位 reviewer 的原话争论、结构化约束面板)重画成一条只有 4 个日期节点的时间线——信息量掉一个数量级,还把"设计知识藏在 review 讨论里"这个核心论点画没了。

**常常最好的答案是两个都要:** 抽原图当忠实底本,配一个交互带听众走一遍。原图保证不失真,交互负责讲清楚——别为了"有交互"就把原图换掉。

## 用 NAV 指路,别的都别加

- nav 词本身就是路线图,每页高亮当前段即可。
- 段落顺序单调递增(nav 里的进度绝不往回跳)——沿用论文结构时这自然成立。
- **反 clutter 铁律:** 不插转场句、不做独立"大纲/agenda"页、不加衔接性旁白。真需要一句话给某段定框,折进那页自己的 lede,不新增元素。

## 故事 vs 附录

- **主线页:** 白话,面向混合听众。VOCABULARY 白名单里的术语要注解,不堆形式化符号。
- **技术附录:** 独立、清楚隔开的一段(自带 nav 词,如 `技术细节`),收纳形式化证明、完整实验表、超参、符号推导——凡是会把主线拖进"读论文而非听讲解"状态的内容都放这里。
